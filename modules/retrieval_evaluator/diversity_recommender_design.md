# Diversity-Aware Recommendation over a SPARQL Knowledge Graph — Design Document

## 1. Motivation

Standard retrieval against a knowledge graph returns items matching a query's
constraints. This project adds a second, complementary retrieval signal:
surfacing items that are *interesting precisely because* they sit outside, or
at the edge of, what the query asked for — either through unexpected
combinations of shared features (intra-pool diversity) or through
outright deviation from the query's own constraints (pinned-feature
surprise). In an ethnographic-museum linked-data context, this same
machinery is also the natural home for **polyvocality** — surfacing
alternative interpretive perspectives on an object, not just alternative
objects.

## 2. Architecture Overview

```
Offline                                   Online
--------                                  ------
Feature/vocabulary discovery              1. Relevance retrieval (SPARQL)
Embedding of feature values                  → core matching pool
Perspective coverage indexing              2. Relaxed retrieval (SPARQL)
(optional clustering for                     → near-miss pool (drop one
 content-level suggestions)                   pinned constraint at a time)
                                           3. Merge → single candidate pool
                                           4. Score pool: pinned-feature
                                              entropy + intra-pool diversity
                                           5. Rank/select items (MMR-style:
                                              relevance vs. diversity terms)
```

## 3. Feature Schema

The method is defined over a **general, unspecified set of features** — the
number and identity of features is expected to vary across queries,
domains, and endpoints, and nothing in the scoring logic assumes a fixed
schema. Each feature is one of two general types:

| Feature type | Treatment |
|---|---|
| numeric/ordinal (e.g. a date, a count) | compared by direct numeric distance |
| free-text / label-bearing (e.g. any categorical property expressed as a URI with a label) | text-embedded — no manual categorical encoding or vocabulary enumeration required |

At query time, some subset of features is **pinned** (constrained by the
query) and the remainder are **free** (left open) — this split, not the
specific identity of the features, is what drives the two scoring terms in
Section 5.

Earlier iterations considered building explicit per-feature vocabularies via
`SELECT DISTINCT` queries and ontology range-class lookups (e.g. following a
"consists of material" property to its declared range class and enumerating
instances), and using SKOS `skos:broader`-style hierarchies for categorical
distance. This was dropped in favor of **embedding each feature's label text
directly**, which sidesteps needing to enumerate the full value space per
feature or per endpoint, and gives semantic proximity "for free" without
manually modeling hierarchies. It also means the pipeline requires no
schema-specific setup step per feature — any label-bearing property can be
plugged in the same way.

### 3.1 Worked example (illustrative, not fixed)

The running example used throughout development used four features:
`year` (numeric), `country_of_origin`, `function`, `material` (all
text-embedded). This is one instantiation of the general schema above, not
a required or expected feature set — a different query, domain, or endpoint
may pin a different number of features, of different kinds, and the scoring
logic (Section 6) is unaffected by that variation.

**Perspective/polyvocality** (relevant in domains such as ethnographic
museum collections, where an item may carry multiple, sometimes conflicting
interpretive descriptions) is best kept as a *pointer back into the graph*
(a reference to whatever node plays the "perspective/agent/context" role for
an item) rather than flattened into a feature value — this preserves the
relational richness (provenance, conflicting viewpoints, related contexts)
that a scalar encoding would destroy. It is only dereferenced at
presentation time, and can be treated as an additional feature (pinned or
free, as appropriate) within the same general schema when a graph exposes
it richly enough to be usable, degrading gracefully to being ignored when
it isn't.

## 4. Retrieval Strategy

Retrieval must not be a strict filter on all pinned features, or every
returned item will trivially match the query and the surprise signal below
will always be zero. Retrieval instead produces:

- **Core pool**: exact matches on all pinned features.
- **Relaxed pool**: for each pinned feature, one query variant that drops or
  loosens that single constraint while keeping the others fixed (candidates
  generated by relaxing one pinned constraint at a time, rather than an
  open-ended embedding-space search).

These are merged into one candidate pool before scoring.

## 5. Diversity Scoring

Given: a query `Q` with `k` pinned features, and a retrieved pool `R` of
items (core + relaxed).

### 5.1 Pinned-feature entropy (query-relative "surprise")

For each item and each pinned feature `f`:

```
dist_f(item) = cosine_distance( embed(item.value[f]), embed(Q.value[f]) )
deviates_f(item) = 1  if dist_f(item) > τ_f
                  = 0  otherwise
```

`τ_f` is a distance threshold per feature (fixed/absolute, chosen so that
"everyone matches" still yields zero deviation — a pool-relative/median
threshold was considered but rejected because it mechanically forces ~50%
of items to "deviate" regardless of how homogeneous the pool actually is,
losing the desired zero-at-homogeneity property).

For each item, sum deviations across the `k` pinned features to get a
deviation count `d ∈ {0, 1, ..., k}`. Let `p(d)` be the fraction of the pool
with that deviation count. The **pool-level entropy** is:

```
H(pool) = − Σ_d  p(d) · log( p(d) )        for d = 0 … k
```

Properties:
- `H = 0` when every item in the pool matches all pinned features (no
  deviation at all).
- `H` is maximal when deviation counts are most evenly spread across the
  pool.
- To compare pools produced by queries with different numbers of pinned
  features `k`, normalize:
  ```
  H_normalized = H(pool) / log(k + 1)
  ```
  (`log(k+1)` is the maximum possible entropy for `k+1` possible outcomes —
  this puts differently-sized queries on a common 0–1 scale.)

Per-item ranking uses the deviation count directly rather than entropy
(entropy is a distributional/aggregate quantity, not a fair per-item score;
using `−log(p(d))` as a per-item score was considered and rejected, since it
does not guarantee that higher `d` yields a higher score — it tracks rarity
in the pool, not magnitude of deviation, and those need not coincide):

```
surprise(item) = d(item) / k
```

### 5.2 Intra-pool diversity (free features)

For each free feature, compute the **average pairwise cosine distance**
between embedded values across all items in the pool:

```
diversity_f = average over all pairs (i, j) in R of
              cosine_distance( embed(i.value[f]), embed(j.value[f]) )
```

No threshold or clustering step is required here — this directly measures
spread, which is exactly what intra-pool diversity is meant to capture (as
opposed to pinned-feature surprise, which is meant to capture deviation
relative to the query).

### 5.3 Reporting

Pinned-feature entropy and intra-pool diversity are reported **separately**,
not merged into one blended score. This preserves the distinction between
two qualitatively different kinds of interestingness a heuristic can
produce:
- high pinned-entropy → "this challenges what you searched for"
- high intra-pool diversity → "more like this, but with real variety"

This separation is also what makes the metric useful for comparing
retrieval heuristics against each other (heuristic A vs. B), since a
heuristic could score high on one axis and low on the other.

## 6. Guardrails

Unconstrained surprise-maximization drifts toward irrelevance. Two
guardrails:
- **Relevance/graph-proximity floor**: a candidate is only eligible for
  ranking if it remains reachable from the query context through some other
  relation (shared provenance, broader concept, co-occurrence in a
  collection/exhibition event) — not merely because it scores well
  numerically.
- **Relaxation-based candidate generation** (Section 4) keeps candidates
  tethered to "a nearby question" rather than allowing arbitrary graph nodes
  to compete purely on embedding distance.

## 7. Open Parameters / Decisions Still Open

- Per-feature threshold `τ_f` for pinned-feature deviation — currently
  planned as a fixed, feature-specific constant; needs empirical tuning.
- Whether to expose the relevance/surprise trade-off (α/β-style weighting,
  or the entropy vs. diversity balance) as a user-facing control, given the
  polyvocality framing favors transparency over a hidden fixed trade-off.
- Whether richer perspective-hierarchy information (SKOS `skos:broader`
  chains over interpretive contexts) is worth incorporating later as a
  refinement to the graph-proximity guardrail.
